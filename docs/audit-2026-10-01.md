### Existing model disclosure

`urlScanner.js` already imports an active trained lexical model (`urlLexicalModel.js`). It was trained on 1,000 PhiUSIIL tuning rows. This audit adds no ML and does not retrain or tune that model. The 1,000 held-out rows are evaluated separately; prior use of this same held-out set limits claims of a fresh independent benchmark.

### Baselines captured before edits

`evaluation/results/audit-before-synthetic.json`: 60 synthetic cases, warning TP=20 TN=30 FP=0 FN=10. `audit-before-phiusiil.json`: 1,000 held-out URLs, 500 phishing / 500 legitimate; warning TP=17 TN=500 FP=0 FN=483. These runs use the real local detection functions without online enrichment. They do not describe full production pipeline accuracy.

### Binary policies (preserved)

Primary **warning policy**: Appears Safe (score >=80) is Negative; Caution (score >50 and <80) and Risk Detected (score <=50) are Positive. Secondary **block policy**: only Risk Detected is Positive; Caution is Negative. Reports show both. Undefined ratios are `null` / N/A, never invented percentages. Scores are safety scores, not phishing probabilities.

## Final verification

Local audit/fixes completed; no commit, push, deployment or production migration was performed. Existing rule thresholds and trained model weights were preserved. Baseline and post-change local predictions are identical by case ID, score and status. Existing working detection features were reused.

### Changes and database

- Extracted the existing URL/message/email/file orchestration into `backend/services/detectionPipeline.js`. The production controller and production evaluation call those same functions; labels never enter their arguments. Evaluation intentionally excludes administrative allowlist overrides, user scan persistence and email notifications.
- Added accuracy, F1, numerical confusion matrices and both warning/block policies to the existing evaluator. Zero denominators produce `null` / N/A; F1 uses the algebraically equivalent `2TP/(2TP+FP+FN)`.
- Added strict-admin evaluation endpoints: `GET /api/admin/evaluations` (catalog/history/policy), `POST /api/admin/evaluations` (start a bounded run), and `GET /api/admin/evaluations/:id` (progress/result). Local mode and production mode are explicitly distinct. At most 100 samples per online run or 5,000 local; no arbitrary client-provided dataset paths.
- Added Admin → Evaluation with dataset/mode/sample selection, counts, metrics, confusion matrix, FP/FN details, JSON download and durable history. The PhiUSIIL file must exist on the server; it is intentionally not committed. `EVALUATION_PHIUSIIL_PATH` can select the existing validated JSONL file.
- Added one `evaluation_runs` table using the existing PostgreSQL/SQLite adapter and portable TEXT/INTEGER columns. No new database service or separate application database. Schema initializes on the next server start. Test databases were isolated temporary SQLite files. Production schema was not changed.
- Evaluation jobs run in the existing single Node service. Restarted unfinished runs become `interrupted`; results are never invented. This is not a distributed multi-replica job queue.
- Client authentication now rejects expired credentials before updating activity, closing the gap between periodic cleanup runs. Existing renewal/recovery behavior is retained.
- Health now queries the configured database on each request and returns 503 on failure, instead of always reporting a healthy configured provider.
- OCR browser testing reproduced empty extracted content under the old CSP. The local worker now runs directly from the same origin; CSP permits WebAssembly compilation without unrestricted JavaScript eval or remote scripts. OCR failures stop the submission instead of silently submitting an empty text extraction.
- Extension 1.0.33 adds toolbar badges, popup live storage updates/reset styling, History API navigation monitoring, and alarm-based safe-host refresh. No additional permissions.
- DNR redirect rules required host access absent from the narrowed manifest. Replaced them with DNR **block** actions; warning pages open separately through the tabs API. Existing rules are replaced on worker startup. Downloads pause while scanning and resume if permitted or checks fail. A failed cancellation no longer claims successful blocking.
- Updated stale browser-test assertions to match existing separate content-warning labels, fixed the mobile-test variable scope, and added actual admin/OCR checks. Historical frozen evaluation artifacts were preserved; their compatibility test excludes only the newly added metric fields when comparing old reports.

Removing `tabs` would restrict automatic access to tab URL fields; `activeTab` is narrower for user-requested DOM access but cannot replace background URL monitoring. Search/webmail matches are already narrower than all-sites access. Backend HTTP access is retained for supported local development; production access is HTTPS.

MV3 behavior was cross-checked against primary documentation: [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [permission declarations](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), [DNR permission requirements](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest), and [Edge MV3 migration](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/migrate-your-extension-from-manifest-v2-to-v3). Edge was actually exercised; a separate Chrome installation was not tested. The installed-extension harness changes only its temporary copy's backend URL/grant to an isolated local backend, retains the real feature scripts and other permissions, and uses synthetic web pages.

### False negatives and false positives

- **Local PhiUSIIL:** 483 phishing URLs missed. Of these, 482 expose no triggered local URL finding; the remaining miss has a safety score of 90. Miss scores were 100 or 90. URL appearance alone lacks the content/context and reputation evidence necessary for many historic phishing examples. This is a genuine detection weakness, not fixed by sample-specific rules.
- **Synthetic local:** 10 misses, scores 100 or 88. Nine have no top-level triggered finding in the exposed trace. Text/email detectors do not expose an exhaustive non-trigger trace; absence of that trace does not prove that every underlying condition was tested.
- **Live PhiUSIIL FN `phiusiil-1916`:** expected phishing; predicted Safe/Appears Safe, score 88. No local URL rule triggered. DNS reported no public A/AAAA records (12-point deduction); VT URL was absent; GSB/URLhaus had no match; PhishTank was unconfigured; AbuseIPDB skipped; static page inspection rejected the nonstandard/non-HTTPS input. It remains a false negative.
- **Live PhiUSIIL FP `phiusiil-1290`:** expected legitimate; predicted Dangerous, score 45. VT reported three malicious engines; static page returned 403.
- **Live PhiUSIIL FP `phiusiil-1454`:** expected legitimate; predicted Dangerous, score 33. VT reported one malicious engine (55-point deduction) plus no public DNS records (12); page DNS lookup failed.
- **Live PhiUSIIL FP `phiusiil-0984`:** expected legitimate; predicted Dangerous, score 45. VT reported three malicious engines; static page inspection completed without a page finding.

These three cases remain FPs against the dataset labels. Current provider disagreement with old labels could reflect changed websites, provider false positives or label staleness; this audit did not adjudicate which. One VT engine currently carries a strong deduction, an identified precision risk. No scoring change was made based on this small sample. Stronger blind evaluation and independent adjudication are required before threshold changes.

Every sampled case has a redacted case reference, expected label, prediction, score, available findings/warnings, explicit absent URL-rule codes, provider checked/error/skipped states and page observations in the JSON artifacts. No missing evidence is synthesized. File paths are below.

### Provider and email evidence

For the 20 live PhiUSIIL cases: VT checked 19 (12 matches, 1 skipped); GSB checked 20 (0 matches); URLhaus URL/Host each checked 19 with 1 error; DNS checked 20 (7 network findings); AbuseIPDB checked 13, skipped 7; PhishTank skipped all 20 due to missing configuration. These are provider result records, not necessarily uncached outbound HTTP request counts.

Page inspection completed for 7 URLs and returned errors/limitations for 13. The historical JSON field `unreachablePageChecks` counts **all page-check errors**, including unsupported HTTP URLs and HTTP 403, and must not be read as 13 confirmed network-unreachable hosts. Those samples stayed in the confusion matrix. Provider errors and missing checks were never counted as successful clean results.

SPF/DKIM/DMARC code and mocked authentication tests pass. Six online synthetic email cases explicitly skipped authentication because fixtures lack raw RFC822 source. No live cryptographically signed email or trusted original SMTP transaction was supplied; live SPF/DKIM/DMARC success is unverified. Copied Gmail text cannot establish these checks. DKIM needs unmodified signed source; SPF needs original SMTP client IP and envelope/HELO identity; DMARC needs alignment with authenticated identities.

File analysis keeps local extension/script/macro indicators distinct from VT antivirus stats and already-existing external sandbox verdicts. Tracking Threats does not execute files or operate a local detonation sandbox. Actual live malicious-file sandbox responses were not exercised. QR-derived links were functionally tested through the real file → extracted links → URL detector path. Browser OCR recognized “Meeting tomorrow at noon” from a generated PNG using bundled production assets. Real QR decoding and non-QR barcode formats were not browser-tested; support depends on BarcodeDetector, with jsQR as QR fallback.

### Remaining limitations

No deployment was requested or performed. Production OCR requires deploying the CSP/worker fix. The new evaluation schema uses the existing adapter but was not integration-tested against a live PostgreSQL instance. Evaluation jobs currently assume one Node service process. Provider limits, missing PhishTank configuration, unavailable historic URLs and old dataset labels limit online evidence. Local recall remains low. Live signed-email authentication, real download enforcement, positive activeTab user-invocation flow, real signed-in Gmail and a separate Chrome browser remain unverified. No protection claim covers pages before the first asynchronous scan completes or guarantees complete redirect history across worker restarts.
